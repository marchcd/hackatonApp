# Афиша — бот для поиска бесплатных и льготных событий в MAX

> Трек «Досуг и развлечения». Хакатон MAX, Минобрнауки России.
> Команда: `<название команды>`

## 1. Назначение решения

Чат-бот в мессенджере MAX, который помогает находить бесплатные и льготные
культурные/городские события — включая мероприятия по «Пушкинской карте» —
без необходимости вручную обходить несколько разных сайтов и агрегаторов
(TimePad, PRO.Культура.РФ и т.д.).

Данные о событиях собираются автоматически из внешних источников по
расписанию, нормализуются в единую модель и хранятся в собственной базе —
бот отвечает пользователю мгновенно, не дожидаясь ответа внешних API на
каждый запрос.

## 2. Основной пользовательский сценарий

1. Пользователь открывает чат с ботом в MAX, отправляет `/start`.
2. Бот присылает краткую инструкцию по командам.
3. Пользователь отправляет `/events <город> [бесплатно] [пушкинская]`,
   например: `/events Москва бесплатно`.
4. Бот возвращает список подходящих событий (до 10 штук) с названием,
   городом, датой и ссылкой на источник.
5. Если пользователь не уверен, какой город/категория есть в базе — команды
   `/cities` и `/categories` покажут доступные варианты.

**Известное ограничение (см. раздел 13):** фронтенд мини-приложения
подготовлен, но на момент сдачи онлайн-этапа не привязан к постоянному 
HTTPS-адресу в кабинете MAX, поэтомуосновной проверяемый 
сценарий — именно текстовый бот, описанный выше.

## 3. Состав и архитектура решения

Слои и пакеты:

| Пакет | Назначение |
|---|---|
| `internal/domain` | Единая модель `Event`, к которой приводятся данные из всех источников |
| `internal/source/timepad` | Адаптер TimePad API (публичный REST, `Authorization: Bearer`) |
| `internal/source/kultura` | Адаптер PRO.Культура.РФ; при отсутствии партнёрского ключа отдаёт заранее подготовленные тестовые данные (см. раздел 11) |
| `internal/ingest` | Планировщик: периодически (`INGEST_INTERVAL`) забирает события из всех источников и сохраняет в БД через upsert |
| `internal/storage`, `internal/repository` | Интерфейс репозитория + реализация на PostgreSQL (`pgx/v5`), включая миграции (`goose`, встроены через `go:embed`) |
| `internal/service` | Бизнес-логика поиска: валидация фильтров, пагинация, единая точка входа для бота и HTTP API |
| `internal/handlers` | HTTP-хендлер `/api/events` для фронтенда мини-аппа |
| `internal/bot` | Интеграция с MAX Bot API: long polling, разбор команд, отправка ответов |
| `internal/config` | Загрузка и валидация конфигурации из переменных окружения |
| `static/` | Фронтенд мини-приложения |

## 4. Стек технологий

- **Язык:** Go 1.26
- **HTTP:** стандартный `net/http` + `http.ServeMux`
- **База данных:** PostgreSQL 16 (образ `postgres:16-alpine`)
- **Драйвер БД:** `github.com/jackc/pgx/v5` (пул соединений `pgxpool`)
- **Миграции:** `github.com/pressly/goose/v3`, SQL-файлы встроены в бинарник через `go:embed`
- **MAX Bot API:** `github.com/max-messenger/max-bot-api-client-go/v2`
- **Внешние источники данных:** TimePad REST API, PRO.Культура.РФ (партнёрский API / мок)
- **Логирование:** стандартный `log/slog` (структурированные текстовые логи)
- **Контейнеризация:** Docker (multi-stage build, `golang:1.26-alpine` → `alpine:latest`), Docker Compose

## 5. Запуск всех компонентов одной командой

```bash
docker compose up --build
```

Поднимет PostgreSQL, применит миграции автоматически при старте приложения и
запустит бэкенд (HTTP-сервер + фоновый ingest + MAX-бот в режиме long
polling) в одном контейнере `app`.

## 6. Переменные окружения

Скопируй `.env.example` в `.env` и заполни реальными значениями:

```bash
cp .env.example .env
```

| Переменная | Обязательна | Назначение |
|---|---|---|
| `POSTGRES_USER` | да | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | да | Пароль PostgreSQL |
| `POSTGRES_DB` | да | Имя базы данных |
| `DATABASE_URL` | да (в compose подставляется автоматически) | Строка подключения к БД |
| `SERVER_PORT` | нет (по умолчанию `:8080`) | Порт HTTP-сервера |
| `MAX_BOT_TOKEN` | да | Токен бота, выданный организаторами хакатона |
| `TIMEPAD_API_TOKEN` | да | OAuth-токен TimePad (dev.timepad.ru) |
| `KULTURA_API_KEY` | нет | Партнёрский ключ PRO.Культура.РФ; при отсутствии используется мок (см. раздел 11) |
| `INGEST_CITIES` | нет (по умолчанию — все города) | Список городов через запятую для ограничения объёма fetch'а |
| `INGEST_INTERVAL` | нет (по умолчанию `6h`) | Периодичность фонового обновления данных |
| `SKIP_INIT_DATA_CHECK` | нет (по умолчанию `false`) | `true` отключает проверку `initData` от MAX Bridge на `/api/events` — **только для локальной отладки**, должно быть `false`/не задано в проверяемой версии |

## 10. Описание работы с данными

- Все данные о событиях приводятся к единой модели `domain.Event`
  (источник, внешний ID, название, город, координаты, даты, цена, признаки
  `is_free` / `is_pushkin_card`, категория).
- Фоновый планировщик (`internal/ingest`) с интервалом `INGEST_INTERVAL`
  запрашивает данные у всех источников и сохраняет их через
  `INSERT ... ON CONFLICT (source, external_id) DO UPDATE` — то есть при
  повторном запуске данные обновляются, а не дублируются.
- Все запросы пользователя (через бота) читают
  **только** из локальной БД — внешние API не вызываются синхронно на
  каждый запрос пользователя.

## 11. Порядок работы с тестовыми данными

Интеграция с PRO.Культура.РФ на момент сдачи **использует заранее
подготовленные тестовые данные**, а не реальное подключение — доступ к
партнёрскому API требует одобрения заявки. Тестовые данные захардкожены в
`internal/source/kultura/client.go` (функция `mockEvents`) и покрывают
несколько городов и категорий, включая события с `is_pushkin_card: true`,
чтобы продемонстрировать соответствующий сценарий поиска и показать, что можно
интегрировать разные сервисы для дополнения общей базы событий.

## 12. Пошаговый сценарий проверки

1. `cp .env.example .env`, заполнить `MAX_BOT_TOKEN`, `TIMEPAD_API_TOKEN`.
2. `docker compose up --build`.
3. Дождаться в логах строк `Migrations applied successfully` и
   `max bot: started`.
4. В MAX найти бота по ссылке `https://max.ru/<username>/start`
   (см. раздел 15 — точный `username` указан на первом слайде презентации).
5. Отправить `/start` — ожидается приветственное сообщение со списком
   команд.
6. Отправить `/cities` — ожидается список городов, реально присутствующих
   в базе на момент проверки.
7. Отправить `/events <один из городов из п.6> бесплатно` — ожидается
   список бесплатных событий в этом городе либо сообщение об отсутствии
   результатов.

## 13. Известные ограничения

- **Мини-приложение не привязано к постоянному URL в кабинете MAX на
  момент сдачи онлайн-этапа.** Фронтенд полностью готов, 
  backend отдаёт его и API `/api/events` для него,
  но платформа MAX требует единоразовой привязки публичного HTTPS-адреса
  через личный кабинет, а бесплатный
  cloudflared-туннель, использовавшийся при разработке, не даёт
  постоянного адреса. План выхода в прод — деплой на VK Cloud с
  постоянным доменом.
- Поиск по городу/категории — точное совпадение без учёта регистра
  (`ILIKE`), не полнотекстовый/нечёткий поиск: опечатка в названии города
  не найдёт совпадений.
- Интеграция с PRO.Культура.РФ работает на тестовых данных до получения
  партнёрского ключа (см. раздел 11).
- При большом `total` у TimePad (десятки тысяч событий) первый прогон
  ingest без фильтра `INGEST_CITIES` может занимать несколько минут
  из-за собственного rate limit TimePad (60 запросов/мин).

## 14. Порядок остановки и повторного запуска

```bash
# Остановить, сохранив данные в БД (volume не удаляется)
docker compose stop

# Запустить снова
docker compose start

# Полная остановка с удалением контейнеров (volume с данными БД сохранится)
docker compose down

# Полная остановка с удалением ВСЕХ данных, включая БД
docker compose down -v
```
